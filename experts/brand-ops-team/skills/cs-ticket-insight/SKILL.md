# 客服工单洞察分析

对客服工单/售后会话记录做主题聚类、时效分析与升级预警，
交付四类产物：工单归因分布、SLA 达标率报告、升级风险清单、话术改进建议。

归因模型与 SLA 口径见 @references/ticket-framework.md，报告骨架见 templates/ticket-report.md。
大样本（≥300 条）统计用 scripts/ticket_stats.py（仅依赖 Python 标准库，非交互）；
小样本直接由 Agent 阅读文本分析。

## 第 1 步 确认数据与业务背景

向用户确认：
1. 数据来源：工单导出 CSV（字段通常含：工单号、创建时间、首次响应时间、解决时间、渠道、问题类型、会话文本、客服 ID、满意度评分、是否升级）；
2. 业务口径：SLA 标准（首响 ≤X 分钟、解决 ≤Y 小时）、升级定义（转主管/投诉平台/舆情）；
3. 分析目的：服务短板定位 / 客服绩效 / 话术优化 / 升级预警规则搭建；
4. 时间范围与对比基准。

字段缺失时不编造；会话文本缺失时降级为纯结构化指标分析，并在报告中说明。

## 第 2 步 数据准备（大样本）

```bash
python scripts/ticket_stats.py --data tickets.csv --config config.json --out ./out
```

配置文件字段（JSON）：
```json
{
  "columns": {"text": "content", "created": "created_at", "first_reply": "first_reply_at",
               "resolved": "resolved_at", "channel": "channel", "csat": "csat",
               "escalated": "is_escalated", "agent": "agent_id"},
  "themes": {
    "物流履约": ["没收到", "物流慢", "破损", "发错", "少发"],
    "退换货": ["退货", "换货", "退款", "七天无理由"],
    "产品咨询": ["怎么用", "成分", "尺寸", "参数", "保质期"],
    "价格促销": ["差价", "优惠券", "价保", "满减"],
    "投诉情绪": ["投诉", "差评", "曝光", "315", "监管"]
  },
  "sla": {"first_reply_minutes": 5, "resolve_hours": 24},
  "escalation_keywords": ["投诉", "曝光", "315", "监管", "起诉", "媒体"]
}
```

脚本输出 `ticket_stats.csv`（主题×条数×占比×平均首响×满意度）、`sla_report.csv`（渠道/客服维度 SLA 达标率）、
`escalation_list.csv`（升级风险工单清单）、`labeled_tickets.csv`（逐条打标）。

**脚本局限（必读）**：关键词子串匹配不识别否定语境；升级关键词命中≠真实升级意图，
Agent 必须逐条复核 escalation_list 后再定级。会话文本含用户个人信息，脚本已做手机号/订单号匿名化，
交付物中不得出现可识别个人的原文。

## 第 3 步 工单归因分析

按 references/ticket-framework.md 三级归因：
1. **一级（问题类型）**：物流履约 / 退换货 / 产品咨询 / 价格促销 / 产品质量 / 投诉情绪；
2. **二级（责任环节）**：仓储 / 物流商 / 详情页信息不足 / 促销机制复杂 / 产品本身 / 客服处理不当；
3. **三级（可改进性）**：客服侧可改（话术/流程）/ 需跨部门协同 / 外部不可控（物流商时效）。

要求：每类问题引用 2-3 条脱敏会话摘录作证据；区分「服务问题」（客服响应/态度/解决力）与
「业务问题」（产品/物流/价格），两者的改进责任方不同。

## 第 4 步 SLA 与时效分析

- 首响达标率 = 首响 ≤SLA 的工单占比，按渠道、客服、时段（工作日/大促期）拆分；
- 解决时效分布：P50/P90 解决时长，长尾工单（>3 天未结）单独列出；
- 时效×满意度交叉：验证"响应快≠满意"，定位一次解决率（FCR）短板；
- 大促期对比：SLA 恶化幅度 >50% 时提示排班与话术库扩容建议。

## 第 5 步 升级风险预警

按 references/ticket-framework.md 的升级信号分级：
- **红色（立即介入）**：监管/媒体/法律诉讼关键词、已投诉平台、VIP 客户激烈情绪；
- **橙色（当日跟进）**：二次进线同一问题、会话中出现"差评/曝光"、解决时长超 SLA 2 倍；
- **黄色（规则观察）**：高客单订单售后、情绪词密集但无升级信号。

每条红/橙工单给出处置建议（谁跟进、话术要点、补偿边界）。

## 第 6 步 话术改进建议

基于高频场景输出话术骨架（承认→方案→补偿→确认），要求：
- 针对「客服处理不当」类工单，对比原话术与改进话术；
- 补偿承诺必须在授权边界内（不承诺无法兑现的赔付）；
- 情绪安抚话术与问题解决话术分开设计；
- 成稿话术过 ad-compliance-check 合规扫描（不得出现诱导撤诉返现等违规表述）。

## 第 7 步 产出报告

按 templates/ticket-report.md 骨架：开头三条核心结论（有数据支撑）→ 归因分布表 →
SLA 达标率（渠道/客服/时段三维）→ 升级风险清单 → 话术改进对照表 → 数据缺口。

## 约束

- 会话文本必须脱敏后才能引用（脚本已自动处理手机号/长数字，Agent 复核昵称与地址）；
- 不做客服个人问责导向：绩效数据只呈现分布，不点名批评个人，改进以流程与话术为主；
- 不编造 SLA 与满意度数据；无时间戳字段时如实说明无法计算时效；
- 升级预警只是辅助信号，最终处置由人工判断；
- 用户提供的工单数据仅用于本次分析。
